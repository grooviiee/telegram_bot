# 응답 속도 개선

모델·4K 문맥·입력/출력 길이·재무 계산·원문 인용과 수치 검증은 유지합니다.
생성 답변을 짧게 자르거나 검증을 생략해서 속도를 높이지 않습니다.

## 근거가 같은 답변 재사용

서술형 `/chat`은 매번 최신 공시 목록 캐시와 색인 판본을 확인해 근거를 고릅니다.
그 후 법인, 질문, 전체 대화 이력, 실제 모델 입력, 근거·접수번호, 모델·문맥·생성
설정, 검증 버전이 모두 같으면 기존 검증 답변을 재사용합니다. 재사용 전에도
동일 인용·수치 검증을 적용합니다. 다른 기업·연도·후속 질문·정정본에는 재사용하지 않습니다.

실패·검증 탈락·원문 폴백 응답은 저장하지 않습니다. 동일한 요청이 동시에 오면
진행 중인 추론 하나를 함께 기다립니다. 한 대기 요청이 취소돼도 다른 요청의
생성을 취소하지 않습니다. 실패한 공유 작업이 끝난 뒤 새 요청은 다시 시도합니다.

회사명 원문을 캐시 키로 쓰고 회사당 최대 16개 변형, 최대 20개 회사를 저장합니다.
캐시에는 질문·대화 원문 대신 SHA-256 지문과 검증 답변을 저장합니다. 답변에 포함된
문구는 캐시에 남을 수 있으므로 기존 로컬 `.cache` 데이터와 동일하게 취급합니다.
`GET /cache/status`의 `report_answers`와 기존 회사별/전체 캐시 초기화에 연계합니다.

응답의 `cached`는 기존처럼 공시 색인 재사용 여부이며 `answer_cached`는 생성 답변
재사용 여부입니다. `response_shared`는 진행 중인 추론 공유 여부입니다.
`timings_ms`는 근거 검색·답변 준비·합계의 서버 처리 시간입니다.

## 검색·비교의 반복 작업 제거

같은 법인·접수번호·색인 생성 시각·질문의 검색 결과는 최대 128개를 메모리에서
재사용합니다. 원문을 다시 색인하면 판본이 바뀌므로 다른 결과를 읽으며,
색인을 명시적으로 삭제할 때 메모리 검색 캐시도 지웁니다.

`/changes`는 먼저 두 보고서의 접수번호·연도·결산월을 확인합니다. 기존 비교
결과와 판본이 같으면 전체 본문을 다시 읽거나 비교하지 않습니다. 정정본 또는
법인·비교/색인 버전이 달라지면 기존과 같은 비교·근거 생성 경로를 실행합니다.

## 모델 준비와 Telegram 대기

서버 시작과 상담 시작 시 빈 로컬 요청으로 모델을 미리 준비합니다. 준비 작업은
백그라운드에서 하나만 실행하며 실패해도 데이터 조회를 막지 않습니다. 모델 사용 후
메모리 유지 시간은 1시간입니다. 모델의 정밀도·GPU 백엔드·출력 설정은 바꾸지 않습니다.
공식 동작은 [Ollama 모델 사전 준비 및 keep_alive 문서](https://docs.ollama.com/faq)를 참고하세요.

Telegram 상담의 HTTP 대기도 백그라운드로 옮깁니다. 한 상담의 이력은 직전 답변이
끝난 뒤에만 갱신하고 중복 입력은 안내합니다. 그동안 다른 명령이나 다른 사용자의
요청은 처리할 수 있습니다. `/end` 또는 새 상담은 이전 대기 작업을 취소하고,
종료 뒤 늦은 답변이 새 상담 이력에 섞이지 않게 합니다.

새로운 질문의 최초 생성은 기존 모델의 추론 시간이 필요합니다. 공시 첫 다운로드,
색인 또는 검증 후 재생성도 여전히 시간이 걸릴 수 있습니다.
